> 解释系统里每个架构决策的**理由与实测依据**。
>

## 1. 为什么拆成多个 Agent

### 真实的拆分理由

一个 Agent 承担全部职责时：

- **Prompt 膨胀**：系统提示词要同时覆盖"解析文档 / 抽实体 / 回答 / 检测变更"，
  约束之间会互相干扰
- **难以调试**：出了问题不知道是哪个环节，日志里只有一次巨大的 LLM 调用
- **无法独立迭代**：改抽取策略会碰到问答的 prompt

拆成四个专职角色后，每个角色的 prompt 只服务一个目标，也各自有独立的失败与重试策略。

### 四个 Agent 的实际角色

| Agent | 职责 | 关键实现 |
|---|---|---|
| `DocParserAgent` | 解析 → 切分；给每块标注 `searchable` / `section_type` | 「文档说明」类章节被标记为**不可检索**，避免抢占召回位 |
| `KnowledgeExtractAgent` | 抽取实体与关系 | 结构化输出 + 指数退避重试（1/2/4/8s） |
| `QAAgent` | 问答主链路 | 见第 3 节 |
| `KnowledgeUpdateAgent` | 变更检测与整篇替换 | 按内容哈希判断是否需要重跑（当前无自动触发）|

### ⚠️ 需要说清的一点：这不是"协作型 Multi-Agent"

四个 Agent 分属**三条互不协作的流水线**，**一次问答只用到 1 个 Agent**。
它们之间没有消息传递、没有委派、没有共享黑板、没有 supervisor。

LangGraph 在这里是**固定边的 workflow 引擎**，不是动态路由的 agent 编排图。

更准确的描述是：**多阶段流水线，每个阶段是一个 LLM 角色**。
（这个区分在面试里比"我做了 Multi-Agent"更经得起追问。）

## 2. 编排引擎：三条流水线

### 为什么用 LangGraph

把流水线建模为有向图，节点是处理步骤、边是数据流。相比直接写函数调用链，
它把"状态"显式化了：每步都能读写同一个 state，失败时能定位到具体节点并单独重放。
（本项目**没有**用条件边做动态路由 —— QA 图是 `answer → END`，
update 图有一条重试边。）

### 流水线 1：文档入库（`ingest`）

```
parse → extract → vectors → commit
```

- `parse` / `extract` **串行**：抽取依赖解析结果
- 每一步都更新 `documents.status`，**失败可定位到阶段并单独重放**
- 为什么分步而不是合并成一步：重新解析 + LLM 抽取是**昂贵操作**
  （每 chunk 一次 LLM 调用），失败时不必从头再来

### 流水线 2：问答（`qa`）

```
answer → END
```

问答的复杂度都在 Agent 内部（意图 → 改写 → 检索 → 精排 → 生成），
外部编排保持单节点。

> 之所以还能切换 `pipeline` / `react` 两种实现，是因为两者对外接口完全一致
> （`answer(question, acl_scopes) -> QAResult`），换实例即可，图结构不用动。

### 流水线 3：文档更新（`update`）

```
process → (有失败?) → retry ──┐
      └────────────→ END     └→ (最多 3 次，指数退避 1/2/4s) → END
```

带**有界重试 + 指数退避**：失败瞬间重试往往撞上同一个问题。

## 3. 检索架构：两阶段检索

```
用户问题
   │
   ├─ ① 意图分类（function calling 强制枚举，服务端约束取值合法）
   ├─ ② 查询改写（1 个问题 → 多个查询变体）
   │
   ▼
阶段一：BM25 多查询并发召回          ← 目标：召回率
   │      （自研 bigram + unigram，零依赖）
   ▼
阶段二：cross-encoder 精排           ← 目标：排序质量
   │      （BAAI/bge-reranker-v2-m3；失败则回退原序）
   ▼
small-to-big 展开 → 取 Top-8 → 生成
```

### 为什么不只用稠密向量

实测（同一语料、同一评测集）：

| 检索方式 | Chunk Recall@5 |
|---|---|
| 稠密向量 | **23.6%** |
| **BM25（采用）** | **89.1%** |

原因是企业制度类语料的查询高度依赖**精确词面匹配**（"密码 长度 位数"、
"住宿 500 元"），稠密向量在这类数值/名词型查询上明显吃亏。
完整诊断过程（含 embedding 参数、两套客户端配置、重建路径 vs 查询路径的排查）
见 [`retrieval-bm25-migration.md`](./retrieval-bm25-migration.md)。

### 为什么不用混合检索（RRF 融合）

实测融合后**比单路 BM25 更差**。BM25 已经吃掉了大部分召回，
稠密那一路引入的噪声反而拉低了排序质量。

## 4. 数据一致性：SQLite 状态机 + Outbox

### 问题

早期实现是"解析完直接写向量库"，没有任何事务或补偿：

```
extract ──┬──> store_vectors ──> END
          └──> store_graph   ──> END      ← 这一步失败会怎样？
```

中途失败时数据状态不可知，且**没有任何地方记录这件事**。

### 方案

`documents` 表作为唯一事实源，状态机推进：

```
PENDING → PROCESSING → VECTOR_DONE → COMMITTED
                 └──────────→ FAILED（超过重试上限）
```

配套：

- **Outbox 表**：把"待做的派生任务"持久化，进程重启后继续消费，不再依赖内存状态
- **`finally` 守卫**：worker 异常时不会留下永久 `PROCESSING` 的僵尸文档
- **`reclaim_stuck_documents()`**：超过 `stuck_timeout_seconds`（默认 1800s）自动回收
- **队列取数在 SQL 层过滤**：早期实现是"先取最新 5 行、再筛 PENDING"，
  结果 20 个 PENDING 永远排不上队（**生产级死锁**）

### 文件变更追踪

`file_versions` 表记录 `source_path` / `content_hash` / `version`，
取代了原来的进程内 `self._file_hashes` 字典（**重启即失忆**）。

## 5. 引用契约（三层分离）

| 层 | 内容 | 用途 |
|---|---|---|
| `RetrievedContext.content` | **命中的那个章节** | 展示与核对 |
| `RetrievedContext.llm_context` | small-to-big 展开后的**父文档** | 只喂 LLM，不返回前端 |
| `display_content` | = `content` | 前端渲染的引用 |

**为什么必须分离**：早期实现把展开后的父文档当引用返回，于是**每条引用的开头
永远是「## 1. 文档说明」**——答案可能是对的，但用户无法核对出处。
实测引用准确率只有 **44.4%**，修正后回到 100%（引用正确率指标 95.6%）。

### 顺带修掉的去重键错误

**必须用块级键 `doc_id#chunk_index` 去重**，不能用文档级的 `parent_id`
（形如 `<doc_id>#doc`）。后者会把同一文档的所有章节折叠成一条，
**静默丢掉命中章节** —— 这是"gold 章节检索不到"的隐蔽根因。

## 6. 生成与可观测性

### 稳定前缀 Prompt

```
system（常量 411 字符，所有问题逐字节相同 —— 这里永不插值）
user（动态，顺序固定）
    <request_metadata>  intent=…
    <retrieved_context> <source id="1" document="…"> … </source> …
    <user_query> … </user_query>
```

- 意图从 system 挪进动态段；上下文标签**不带分数/类型**（分数每问必变，会打断前缀复用）
- 有测试钉住"换意图/换问题 system 段必须逐字节相同"
- 诚实说明：这项改造的**缓存收益实测落在噪声内**（−1.2pp），
  真正收益是引用准确率 **+15.6pp**（80.0% → 95.6%）

### 可观测性

- **结构化日志**：每个请求一个 `request_id`（ContextVar），JSON 或文本两种格式
- **用量计量**：每轮问答记录 token / 缓存命中，并把命中拆成
  ① 总命中率 ② 稳定前缀复用率 ③ 检索上下文复用率；
  每次模型调用按 stage（`intent` / `rewrite` / `generate`）展开
- **对话历史**：每轮快照落库，刷新后恢复界面（**不注入 prompt**，单轮语义不变）
- **审计日志**：`qa.ask` / `doc.upload` 等敏感操作落库

细节见 [`chat-metrics.md`](./chat-metrics.md) 与 [`conversation-history.md`](./conversation-history.md)。

## 7. 数据流总览

```
                    ┌──────────────────────────────┐
                    │           用户操作            │
                    └───────┬──────────────┬───────┘
                            │              │
                     上传文档 │        提问   │
                            ▼              ▼
                    ┌───────────┐   ┌───────────┐
                    │ 入库流水线 │   │ 问答流水线 │
                    └─────┬─────┘   └─────┬─────┘
                          │               │
                          ▼               ▼
                    ┌───────────┐   ┌───────────┐
                    │  向量索引  │←──│ BM25 召回  │
                    │  Chroma   │   │ + 精排     │
                    └───────────┘   └─────┬─────┘
                          ▲               ▼
                    ┌─────┴─────┐   ┌───────────┐
                    │ SQLite    │   │  LLM 生成  │
                    │ 状态机+Outbox│  └───────────┘
                    └───────────┘
```

**没有图数据库、没有消息队列、没有外部服务。**

## 9. 已知限制

见 README 的「已知限制」一节。最关键的两条：

1. **单进程假设**：`turn` 取号依赖 SQLite 单进程内写锁，多 worker 部署会重号
2. **ACL fail-open**：文档缺 ACL 元数据时**默认放行**

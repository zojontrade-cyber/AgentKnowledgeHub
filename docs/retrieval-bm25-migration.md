# 检索架构变更报告：稠密检索 → BM25 主召回

**日期**：2026-09（本次会话）
**范围**：`python/services/`、`python/config/settings.py`
**状态**：已落地，87 单测通过，端到端验收通过

---

## 一、结论先行

企业制度知识库的**主召回通道从稠密向量检索改为 BM25**。

在 159 个制度章节、78 题文档级 / 55 题 chunk 级评测集上（retrieval-only，无 reranker）：

| 方法 | Doc Top-1 | Doc R@5 | Doc MRR | Chunk Top-1 | **Chunk R@5** | Chunk MRR |
|---|---|---|---|---|---|---|
| 稠密（Qwen3-Embedding-8B） | 16.7% | 41.0% | 0.302 | 5.5% | **23.6%** | 0.131 |
| **BM25（新默认）** | **78.2%** | **93.6%** | **0.854** | **47.3%** | **89.1%** | **0.637** |

两个独立实现（实验脚本 / 生产代码路径）得到**完全一致**的 89.1% / 23.6%，可交叉验证。

## 二、为什么要改

### 2.1 现象

用户报告："入库之后用智能问答，找不到信息。"

实测复现（真实生产向量库，159 条向量，走 `VectorStoreService.search`）：

```
Q: 请假要走什么流程
  1. [0.5971] 离职交接管理办法 / 1. 文档说明     ← 正确答案排名 >20
     本办法规范员工离职时的工作交接、资产归还…

Q: 年假有多少天
  1. [0.5974] 印章与证照管理制度 / 2. 印章范围   ← 完全无关
     公司印章包括公章、合同专用章、财务专…
```

"请假"、"年假" 这些词**根本没出现在胜出的 chunk 里**。它们靠共享的
"本办法规范…" 套话骨架胜出。

### 2.2 根因

制度语料含大量**判别性极强的低频词项**：请假、年假、保密、印章、报销、打卡。

| 词项 | 制度文档频次 | huatuo 语料频次 |
|---|---|---|
| 请假 | 4 | 0 |
| 年假 | 5 | 0 |
| 保密 | 16 | 0 |
| 印章 | 10 | 0 |
| 报销 | 15 | 0 |

- **BM25**：这些是天然的高 IDF 强信号
- **稠密模型**：4096 维空间把"请假"与"离职"压得很近，而 30 篇制度
  都在讲"流程"，全部得分挤压在 0.44-0.60 区间，**没有区分度**

这不是参数问题 —— 实测三种 embedding 输入形态（A 当前 / B 五段强上下文 /
C 去套话）**全部 Top-1 = 0/6**。问题在检索范式，不在输入构造。

### 2.3 RRF 融合被证伪

| 方法 | Chunk R@5 |
|---|---|
| BM25 | **89.1%** |
| RRF 等权 | 50.9% |
| RRF 权重 0.3:0.7 | 70.9% |

**任何形式的融合都低于纯 BM25。** 机制：

```
gold:  dense_rank=66（被截断，投 0 票）   bm25_rank=1
       → RRF 合计 0.016393，排第 19

竞争者: dense_rank=3, bm25_rank=14
       → 两路都投票，RRF 合计 0.031258，排第 1
```

RRF 奖励"两路都还行"，而非"一路极好"。当一路是噪声时，融合**放大噪声**。

## 三、改了什么

### 3.1 新增 `python/services/bm25.py`（~150 行）

```
tokenize(text)         中文分词：字符 bigram + 单字（零依赖，不用 jieba）
BM25Index              内存索引，RLock 线程安全
  .build(texts, ids)   (重)建索引，O(N·L)，159 篇约 10ms
  .rank(q, k)          → [(位置下标, 分数)]
  .rank_ids(q, k)      → [(外部主键, 分数)]  ← 检索层用这个
  .size                文档数
```

**关键设计**：`ids` 存 **Chroma 的真实 chunk_id**（形如
`89d0959c15cea16c#chunk-0`），不是位置下标。早期实现用位置下标去
`store.get(ids=["0","1",...])`，导致取回永远为空 —— 已修复并加长度校验。

**为什么用 bigram 而非 jieba**：零依赖；对未登录词（"云启科技"、"OA 系统"）
鲁棒；实测 89.1%，无需引入分词器。

### 3.2 `python/services/vector_store.py`

| 变更 | 说明 |
|---|---|
| 新增 `_bm25` / `_bm25_stale` 字段 | 懒建索引 + 失效标记 |
| 新增 `_ensure_bm25()` | 首次检索或写入后重建；索引文本用 `display`（含标题路径）|
| 新增 `_mark_bm25_stale()` | `add_chunks` / `delete_by_doc_id` / `reset_collection` 调用 |
| `search()` 改为按 `settings.retrieval_mode` 路由 | bm25 / dense / hybrid |
| 新增 `_search_bm25()` | 主通道；BM25 不可用时回退稠密（可用性优先）|
| 新增 `_search_hybrid()` | 保留仅供对照，注释明确标注"实测低于纯 BM25" |
| 原 `search()` 稠密逻辑 → `_search_dense()` | 降级为对照/回退 |

**为什么 BM25 索引用 `display` 而不是 `content`**：与稠密相反。稠密要纯净
正文（避免套话主导），BM25 依赖**字面命中** —— 用户问"差旅报销"时，
"差旅报销管理规定"这个标题本身就是最强信号。

### 3.3 `python/config/settings.py`

```python
retrieval_mode: Literal["bm25", "dense", "hybrid"] = "bm25"
hybrid_bm25_weight: float = 0.7
```

用 `Literal` 约束，拼错立即报错（沿用本项目既有约定）。

## 五、语料范围锁定（本次一并确认）

| 层 | 内容 | 状态 |
|---|---|---|
| **制度 retrieval corpus** | 159 章节（30 篇） | **锁定，BM25 主召回** |
| Huatuo QA（2000 篇） | 未来独立 QA layer | 语料已恢复，**未入库** |
| Dense | 对照组 / 回退 | **不作为主召回** |

### 关于 huatuo 的重要发现

1. **`corpus/` 曾是空目录** —— 导致 `bulk_ingest.py:157` 静默空转
   （打印"没有需要处理的文档"，退出码 0）。已用 `prepare_huatuo.py`
   确定性重建（`random.seed(42)`），2000 篇已落盘。
2. **85% 的 huatuo 文档 <30 字**（中位数 9 字），会被 `is_indexable`
   质量闸门拒绝。它是 QA 答案字段碎片，不是可切块文档。
3. **繁体仅占 0.3%** —— 原以为的简繁问题在 huatuo 上不成立。
4. **词汇冲突极小**：bigram 交集仅占制度词表 10.7%，全部判别词
   （请假/年假/保密/印章/报销）在 huatuo 中出现 0 次。**因此混合
   索引不会稀释 IDF** —— 分离的理由是产品语义，不是技术污染。

## 六、已知局限 / 未做

1. **BM25 是全量内存实现**。159 章节可忽略；语料上万需换磁盘索引。
2. **hybrid 模式保留但已知更差**。若今后稠密模型更换（如换更强的中文
   领域模型），应重跑 P1 再判断。
3. **无 BM25 + Reranker 组合数据**。用户提出的 P2 尚未执行。
4. **两阶段检索（文档级→章节级）未落地**。实测 MRR 0.039→0.394 有明显
   改善，但当时根因未定位，需在 BM25 基础上重新评估收益。
5. **"1. 文档说明"章节未排除**。已确认其系统性污染召回（信息量低、
   套话重、排名虚高），用户已同意排除但保留父块供 small-to-big 展开 ——
   **尚未实施**。
6. **tokenize 的 bigram 策略未与 jieba 对比**，也未做 k1/b 调参。
